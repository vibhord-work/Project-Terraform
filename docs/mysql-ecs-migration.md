# RDS to ECS-hosted MySQL migration

## Target architecture now provisioned by Terraform

- Existing ECS cluster, with one dedicated private ECS EC2 host for MySQL.
- Dedicated host defaults to t3.small and registers with ECS using custom attribute role=database.
- Separately managed encrypted gp3 EBS data volume, mounted at /mnt/mysql-data on the host and bind-mounted to /var/lib/mysql in the MySQL 8.0 container.
- ECS service placement constraint pins the MySQL task to the dedicated database host.
- Cloud Map private DNS name mysql.db.internal.
- MySQL task security group permits TCP/3306 only from the application ECS task security group.
- MySQL credentials are generated by Terraform and stored in Secrets Manager; task execution role can read only the required secret.
- CloudWatch log group /ecs/project-poc-mysql (name follows project/environment variables).
- RDS remains provisioned, encrypted, deletion-protected, and protected by Terraform prevent_destroy.

## Important implementation detail

The database uses a separately managed EBS volume and an explicit host mount. It does not rely on ECS-managed task EBS volumes, which are deleted when tasks managed by an ECS service terminate. The EBS volume has prevent_destroy enabled. Back up the volume and test restore procedures before any host replacement or decommissioning.

The database host is single-AZ and the MySQL service has one task. This is a cost-conscious POC design, not a highly available production database. A host or AZ failure interrupts database access until the host/volume is recovered.

## Deployment phases

### Phase 1 — Provision target without switching the application

Keep the default:

```hcl
use_ecs_mysql = false
```

Run from the Terraform repository root:

```bash
terraform init
terraform fmt -check -recursive
terraform validate
terraform plan -out=tfplan
terraform show tfplan
```

Review the plan. It should add the dedicated database host, EBS data volume and attachment, Secrets Manager credentials, Cloud Map, CloudWatch log group, MySQL task definition/service, and required security/IAM rules. It must not destroy or replace RDS.

Apply only after plan review. Wait for the ECS MySQL service to reach RUNNING and pass its container health check. Verify the ECS instance is registered with attribute role=database, the volume is mounted at /mnt/mysql-data, and the service is discoverable at mysql.db.internal.

### Phase 2 — Snapshot and migrate existing RDS data

1. Create a manual RDS snapshot and wait for it to become available.
2. Use a private migration host with MySQL client tools and access to both RDS and the ECS database service.
3. Export a transactionally consistent dump from RDS. Keep the dump encrypted and outside Git; use private encrypted storage with tightly scoped access.
4. Import the dump into the ECS MySQL service.
5. Compare schemas and table counts. Validate key records for patients, appointments, doctors, nurses, prescriptions, bills, treatments, tests, staff, wards, and equipment.
6. Test application reads and writes against ECS MySQL while the production backend remains connected to RDS. Use a separate validation client or temporary task definition.
7. Schedule a short maintenance/read-only window, take a final consistent export, import the final delta, and repeat validation to avoid losing writes made after the first export.

Do not put database dumps, passwords, or connection strings in the repository, PR, logs, or shell history.

### Phase 3 — Switch the backend

Only after the data import and application-level verification succeed, set:

```hcl
use_ecs_mysql = true
```

Review the Terraform plan. It should create a new backend task-definition revision using DB_HOST=mysql.db.internal and the new Secrets Manager credentials. RDS must remain running and protected.
Important: the existing backend ECS service intentionally ignores Terraform changes to task_definition so Jenkins deployments are not overwritten by routine Terraform applies. Therefore, after Terraform apply, explicitly deploy the new task-definition revision:

~~~bash
CLUSTER=$(terraform output -raw ecs_cluster_name)
SERVICE=$(terraform output -raw backend_ecs_service_name)
TASK_DEF=$(terraform output -raw backend_task_definition_arn)
REGION=$(terraform output -raw aws_region)

aws ecs update-service \
  --cluster "$CLUSTER" \
  --service "$SERVICE" \
  --task-definition "$TASK_DEF" \
  --force-new-deployment \
  --region "$REGION"

aws ecs wait services-stable \
  --cluster "$CLUSTER" \
  --services "$SERVICE" \
  --region "$REGION"
~~~

Then test patient login, patient creation, doctor/staff views, appointments, bills, prescriptions, and other application workflows. Keep the previous task definition revision available for rollback.

### Phase 4 — Rollback window and eventual RDS retirement

If application checks fail, set use_ecs_mysql=false and redeploy the backend to reconnect to the still-running RDS instance. If writes have occurred on ECS MySQL after cutover, reconcile them before switching back to avoid data loss.

Keep RDS and its snapshots for an agreed rollback window. RDS retirement is a separate change requiring explicit approval, verified backups, and a final reviewed Terraform plan. Do not remove prevent_destroy or deletion protection as part of the initial migration.

## Operational recovery

- Before host maintenance or replacement, stop the MySQL ECS service and create an EBS snapshot.
- Preserve the EBS volume. Never format an existing non-empty data volume automatically.
- Reattach the volume in its original Availability Zone and mount by filesystem UUID.
- Start the ECS agent only after the volume is mounted, then allow the ECS service to place the MySQL task.
- Test EBS snapshot restore in a separate volume before relying on it for recovery.

## Cost and availability considerations

The design adds a t3.small EC2 instance, gp3 EBS storage, snapshots, networking charges, and operations. Compare this total with the current db.t4g.micro RDS cost. The ECS-hosted option trades managed database operations, automated backups, and managed failover for more control and a potentially different cost profile. It is not automatically cheaper.
